Build the Resolver — the MVP

The most minimal possible version of the product: a share extension that turns any song link into a universal link, running on your own iPhone with no App Store, no approval, no paid developer account. Recipient side is free.

Scope minimal viable product · By L · Prereq a Mac with Xcode  ·  Companion to report no. 001 (the research)
Part 0 — The product build
§ 00

What we're building

One tap, no friction: share a song → it lands as a universal link that opens in the recipient's own streaming app.

1
You share a songfrom Spotify, Apple Music, YouTube, Tidal — tap the system Share button.
2
Tap our appit appears in the share sheet because it declares "I accept links."
3
The extension resolves the linktakes the raw song URL, wraps it as https://song.link/{url}.
4
The extension presents the native share sheetthe real iOS share sheet appears, right from the extension, with the song.link ready — exactly like sharing any link from any app. No host app hop needed.
5
Tap WhatsAppexpected: a normal rowin that sheet; picking it opens WhatsApp with the song.link already in the message. Pick the chat, send. GATED by the § 09 device test — observe on-device, don't assume.
Why no host hop? iOS does not let a share extension open another app — NSExtensionContext.open is scoped to Today widgets and iMessage apps only, and the old UIApplication.openURL workaround is blocked on iOS 18. So the extension presents the share sheet itself (via UIActivityViewController), staying entirely inside Apple's sanctioned extension surface. Details in § 03.
Zero backend. For the MVP, the "resolver" is literally the public song.link service. Our app just hands the song URL to it. The matching engine you'd eventually build is not needed for the MVP.
§ 01

The two files that are actually the app

An iOS share extension cannot exist alone — it must live inside a host app. But the host's job for the MVP is just to exist: the extension itself presents the native share sheet (see § 00). The host is literally an empty container.

§ 02

The file that makes it appear — and resolve

The extension's Info.plist declares what it is (a share service), what it accepts (URLs — and plain text so links shared as text still resolve) and which class runs it. There is no host hop, so the host needs no custom URL scheme at all.

// EXTENSION Info.plist — the whole "share sheet" magic
    NSExtension
      NSExtensionPointIdentifier   = com.apple.share-services
      NSExtensionPrincipalClass     = $(PRODUCT_MODULE_NAME).ShareViewController
      NSExtensionAttributes
        NSExtensionActivationRule     = // { String predicate: only bites when a shared item holds a URL, or plain text }
        SUBQUERY(extensionItems, $i,
          SUBQUERY($i.attachments, $a,
            ANY $a.registeredTypeIdentifiers == "public.url"
            OR ANY $a.registeredTypeIdentifiers == "public.plain-text"
          ).@count > 0
        ).@count > 0

NSExtensionPointIdentifier = com.apple.share-services is the line that turns it into a share-sheet entry. The ActivationRule predicate makes it appear specifically when you share a URL or link-as-text rather than cluttering every share sheet. Use the fully-qualified $(PRODUCT_MODULE_NAME).ShareViewController principal class — a bare ShareViewController leaves Xcode unable to find the class at launch.

// Delete any NSExtensionMainStoryboard / MainInterface.storyboard
    // — the plain view controller (§ 03) needs a principal class, not a storyboard entry.

The extension itself presents the share sheet (§ 03), so no CFBundleURLTypes scheme is needed on either target. The old "resolver:// hop to the host" is not sanctioned — iOS scopes NSExtensionContext.open to Today widgets and iMessage apps only, and blocks every direct app-open path from a share extension — except the responder-chain UIWindowScene.open (§ 09), which is undocumented,and sideload-only. That's why the host is an empty container.

§ 03

Two short files — the whole app

// ShareViewController.swift — the ONE functional file.
//
// What it MUST do (the whole product), in order:
//
//  1. On appear: iterate every attachment (extensionContext.inputItems.flatMap attachments).
//  2. For each, check hasItemConformingToTypeIdentifier("public.url"). If found, load that item
//     as a URL; else fall back to "public.plain-text" and detect a URL in the text.
//  3. Resolve: build https://song.link/{url}. Do NOT string-interpolate the raw URL into a query —
//     ampersands ( & ) and question marks in the raw link break the URL. Build it so they
//     percent-encode the source URL as one path segment ( RFC 3986 pchar): encode
//     every byte not in [A-Za-z0-9-._~], so `:` `/` `?` `&` become %3A %2F %3F
//     %26. Example: https://open.spotify.com/track/123?si=abc -> https://song.link/https%3A%2F
//     %2Fopen.spotify.com%2Ftrack%2F123%3Fsi%3Dabc. One-time dev check: open the built https://song.link/ in Safari once before shipping
//  4. Present: build the link metadata first,then hand it to the sheet:
//     let md = LPLinkMetadata(); md.title = resolvedUrl.absoluteString    // bare baseline, no network
//     md.originalURL = resolvedUrl; md.url = resolvedUrl         // rich preview lands on the link itself
//     md.imageProvider = nil                                         // no fetch, so no thumbnail either.
//     Optional real title: dead - the Odesli/Songlink API is retired; skip for the MVP.
//     let itm = UIActivityItemSource(placeholderItem: resolvedUrl as Any)
//     itm.activityViewControllerLinkMetadata(_:) -> LPLinkMetadata? { md }
//     itm.itemForActivityType(_:_:) -> Any? { resolvedUrl }         // payload the share sheet hands onward
//     present UIActivityViewController(activityItems: [itm],applicationActivities: nil)
//     from THIS view controller. NO host hop,NO SLComposeServiceViewController UI.
//  5. DON'T call completeRequest right after present - it kills the sheet before the user acts.
//     Call it inside the sheet's completionWithItemsHandler,on completed AND cancelled,to end the session.
//     NO-URL path: no attachment held a URL,text held none,or an item load failed - call
//     extensionContext.cancelRequest(withError:),or completeRequest( - never leave an empty view hanging.
//     Several attachments/URLs: use the FIRST public.url you find,stop enumerating.

//     Detect link-in-text with NSDataDetector(link type),then percent-encode ONLYthe matched URL.

// Keep the whole class ~40 lines. UIKit delivers UI callbacks on the MAIN thread.Background
// callbacks come only from NSItemProvider.loadItem/loadObject completion handlers - hop to main there. 
// No force-unwraps on optional URL parts.

// ResolverApp.swift — the host app. EMPTY by design.
import SwiftUI
@main
struct ResolverApp: App {
  var body: some Scene { WindowGroup { EmptyView() } }
}

This is the "normal share" behavior you asked for. The extension resolves the link → UIActivityViewController appears, right from the extension, with the song.link ready. WhatsApp is a normal row in that sheet; tapping it opens WhatsApp with the link pre-filled — gated by the § 09 device test,observe on-device. No copying, no pasting. The host app is a static empty shell — it exists only because Apple requires every extension to live inside one. Its exact Swift syntax is trivial and left to the build agent.

§ 04

Get it on your iPhone — no App Store

A free Apple ID (Personal Team) is enough. No approval, no $99, no review — review only applies if you distribute.

  1. Have a Mac with Xcode. This is the one hard requirement — Xcode is the only tool that can sign and install to an iPhone.
  2. Add your Apple ID in Xcode → Settings → Accounts → “+” → Add Apple ID. This creates a free Personal Team.
  3. Set Signing Team to your Personal Team in the project's Signing settings.
  4. Plug in your iPhone — connecting it to Xcode once makes the Developer Mode toggle appear it often stays hidden until the device has been tethered,or a sideload was attemptedDon't run yet
  5. Enable Developer Mode — Settings → Privacy & Security → Developer Mode → toggle on iPhone must be iOS 16 or later;it prompts for a rebootWithout this, the sideload install fails
  6. Hit Run — Xcode signs,installs,and launches it directly. Re-connect only to renew the 7-day sign each week
  7. Trust it: Settings → General → VPN & Device Management → Trust your Apple ID profile.
  8. Done. Share a song → your app appears in the share sheet.
The catches: (1) free-account installs are signed for 7 days, then you re-run from Xcode to renew; (2) Apple's free tier caps at 3 apps per device and 10 App IDs per 7 days — fine for a single project on one phone; (3) minimum OS is iOS 16 (Developer Mode and the modern share sheet need it). The paid $99/yr Developer Program removes the 7-day and device caps but still needs no App Store review for personal builds — review is only for public distribution;(4) the extension's bundle ID must be a child of the host's — e.g. com.you.resolver.ShareExt —,both targets set deployment iOS 16,and each build eats 2 of the 10 App IDs per 7 days.
Make it one tap, forever - the real setup-once: iOS cannot pin your action for you. Pinning is a user decision,so guide them once:in the share sheet's app row (the short list up top is AirDrop,and other people;our action sits deeper near the other apps),tap More,then Edit,and tap the green + to move it into Favorites. Now it sits near the top of the app row,not buried under More. Icon: the row shows the host app's icon ( the extension inherits it actually. So give it a real one - a blank/default glyph reads as broken in the row.
§ 05

Why the recipient needs to do nothing

"Select which app to open" is the fallback, not the default.

A universal link (song.link/…) is a redirect layer: when the recipient taps it, the landing page detects their device/browser and tries to open their installed app. Truth check: song.link rarely hard-redirects. In practice it mostly shows a chooser/list with their likely app first — and remembers their last choice — so open-in-app happens where detection is confident,. otherwise it's a friendly chooser, a tap away. Your own resolver would do the same thing later; song.link does it for free.

0
app installs the recipient needs — any phone, any browser
1
tap to open in their platform — remembered chooser first, auto-open where confident
$0
backend for the MVP — song.link is the resolver until volume justifies building your own

§ 07

What's deliberately left out (of the MVP)

  • No custom contact picker / recents / per-contact preferences — WhatsApp is reached in the MVP through the system share sheet (tap it, pick a chat), not through our own in-app contact UI. Our own picker, favorites, recent-share history and per-contact platform prefs are the next layer. The MVP proves the core: share → universal link → send.
  • No own matching engine — song.link resolves for you. Build the ISRC layer only when volume justifies it.
  • No Android — separate build; this MVP is iPhone only.
  • No App Store / TestFlight — sideload to your own device is the entire point.

The goal of the MVP is not a product. It's proof: one song, one tap, one universal link, zero friction — running on hardware you hold.

§ 08

Engineering skills — recommended in unison

A build is only as honest as its plan and its review. These four skills run together, in the order the workflow wants: plan → review → execute → compound. Installed on this machine as the Every Inc Compound Engineering tree.

SkillRole in this buildStep
ce-planTurns the brief into a verified build plan — re-checks every iOS 18 / song.link fact against reality before you start1
ce-code-review · swift-iosSwift/iOS reviewer persona — hunts the three bugs that bite a share extension: state, memory, concurrency2
ce-workExecutes the plan with quality gates — finishes the feature instead of leaving half-built scaffolding3
ce-compoundCaptures what you learned (the song.link contract, how the extension presents the share sheet) so the next build starts from knowledge4

The loop: ce-plan → ce-code-review → [revise] → ce-work → ce-compound. Each cycle makes the next unit easier — that's the "compound."

Reference: this is the same discipline as Wayfinder by Matt Pocock — charting a chunk of work too big for one session as decision tickets, resolved until the route is clear. Wayfinder isn't installed yet; the CE tree covers its planning function. If you want it added, that's a separate step — this brief only recommends.
§ 09

Handoff — what the build agent needs

This brief is a handoff artifact: hand it (and report no. 001, the research) to a capable agent and it should be able to build the Resolver. Two things make that handoff actually work.

1. The build order is fixed. Don't let scope creep win. The MVP is exactly two pieces — an empty host app and one ~40-line share extension. If the agent starts adding UI, recents, or an own-matching engine, it's building the wrong thing. Keep it minimal by design.

2. Run the review lineup before you call it done. These personas catch what a first build misses:

ReviewerWhy it matters here
ce-adversarial-reviewerActively tries to break the implementation — failure scenarios for the extension's async load and URL handling, not just "does it match the pattern."
ce-scope-guardian-reviewerChallenges anything that isn't the stated goal. This is the anti-scope-creep gate — the whole point of the MVP is minimal.
ce-swift-ios-reviewerSwift/iOS correctness: state, memory, concurrency — the three classes of bug that silently break a share extension on iOS 18.
ce-security-reviewerChecks the URL input handling — the extension takes external input ( the shared song URL), resolves it to song.link,and feeds it to UIActivityViewController; it must not misfire, misparse,, or leakunexpected content. No host hop, so nothing leaves the sandbox unintended.
The line that matters for handoff: the agent should be able to take this document and produce the code,the Info.plist keys, and the sideload steps without asking the human for clarification. If anything here reads ambiguous, it's a gap in this brief — flag it before building, not after.
One device test gates the whole architecture: after building verify on a phone,with these exact inputs: share from Spotify (it shares a URL)and from Apple Music or YouTube (they may share plain text). Pass means:(1) the WhatsApp's own row appears inside the UIActivityViewController we present from inside the share extension,(2) tapping it opens WhatsApp's own composer with the exact song.link text,(3) sending lands cleanly,and(4) the extension closes cleanly after both send and cancel. The people-suggestions row ( drawn from WhatsApp's INSendMessageIntent donations)is something to record not assume:whether it shows inside a sheet launched from an extension is unknown. If (1) or (2) fails,the last hedge left is responder-chain UIWindowScene.open(_:options:completionHandler:),undocumented,App-Review-risky,and sideload-only.To use it,reach a scene by walking view.window?.windowScene,or the responder chain,and call completeRequest only after it finishes,or on cancel.Name the scheme explicitly: whatsapp://send?text=.Percent-encode the resolved link AGAIN as a query value:its own % signs become %25,,so %3A becomes %253A. Test on the phone current iOS,2026 = iOS 26,not just 18.If the WhatsApp path cannot be made to work,the real fallback is paste:write the song.link URL to UIPasteboard.general,and tell the user to paste manually - never resolving to nothing.And call completeRequest on cancel too,so the extension always closes on its own.Do not ship a buildthat resolves then does nothing.and while you are there,have the tester pin the app to Favorites (see Section 04) so they judge the normal one-tap path rather than the deep-scroll one.
